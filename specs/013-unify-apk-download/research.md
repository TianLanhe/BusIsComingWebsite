# 研究：统一 Android APK 下载入口

## 研究问题 1：顶部与中下部当前到底有什么不同

### 证据

- `frontend/src/components/hero/HeroIntro.tsx` 直接渲染带稳定地址和建议文件名的链接。
- `frontend/src/components/download/DownloadSegmentedButton.tsx` 在点击后执行
  `fetch → response.blob() → URL.createObjectURL() → 临时 a.click() → revokeObjectURL()`。
- 两处最终访问的是同一个服务端下载地址，区别发生在浏览器端，不是后端返回了两个安装包。

### 结论

顶部把下载交给浏览器下载管理器；中下部先把完整 APK 读进页面内存，再把内存对象复制给下载
管理器。后者多了完整缓冲、Blob 分配、临时 URL 和合成点击步骤。

## 研究问题 2：为什么手机上中下部更容易停在 99%

移动浏览器在中下部流程中需要先完整接收响应，之后创建 Blob，并再次把 Blob 交给下载管理器。
页面显示的“正在准备”只能反映 JavaScript 流程，不能代表系统下载已经落盘。较大的二进制文件、
内存压力、浏览器对合成点击/临时 URL 的限制，以及点击后立即回收 URL，都会让最后一步比原生
导航下载更脆弱。

这解释了“顶部能下、中下部 99%”与服务端 APK 字节本身正常可以同时成立：服务端对象相同，
浏览器执行路径不同。

## 研究问题 3：当时为什么采用两种方式

### 中下部历史选择

提交 `8370540 feat: add Android APK download flow` 把早期的直接
`window.location.assign` 改成 fetch/Blob，并引入 `downloading/failed` 状态。目标是：

- 点击后在原位置显示“正在准备下载”；
- 在前端捕获非 2xx 响应并显示三语失败文案；
- 不离开当前页面。

这个方案优化了页面内反馈，却让页面承担了大文件传输和下载交接。

### 顶部历史选择

提交 `3a9055d6 Implement homepage UI optimization` 为 Hero 增加直达主下载 CTA，直接使用
浏览器链接；中下部继续保留既有备用入口逻辑。此时两处强调的产品目标不同：

- 顶部：首屏主转化，点击即下载；
- 中下部：带原位状态反馈的备用下载入口。

后续元数据功能又让两处共享版本/大小显示，但没有统一实际下载执行路径。

## 研究问题 4：哪种方式更适合当前需求

选择浏览器原生下载链接，原因如下：

1. APK 属于大文件附件，不需要页面读取或转换内容。
2. 浏览器下载管理器更适合处理文件名、权限、落盘、重复下载、后台和系统通知。
3. 页面不再维护无法准确代表系统下载完成度的状态。
4. 顶部已有生产证据，实际手机上能顺利完成同一文件下载。
5. 两处共用同一语义后，自动化测试和维护成本更低。

拒绝继续修补 Blob 流程（例如延迟回收 URL），因为这只能缓解一个兼容点，仍保留完整缓冲、
双重内存/复制和页面模拟下载的根本复杂度。

## 研究问题 5：元数据检查应该承担什么职责

### 决策

- 元数据只判断“现在是否可以向用户开放入口”，并提供版本、大小、文件名和稳定下载目标。
- `loading` 时两个入口都不可操作。
- 合法 `200 available` 时两个入口同时变为原生下载链接。
- HTTP 失败、网络失败、JSON 失败或字段校验失败时两个入口都变为不可用。
- 同一 `document` 只检查一次；语言切换只重新格式化文案。
- 不自动重试，不回退旧值，不在元数据检查中读取 APK bytes。

### 边界

元数据成功只代表检查时可用。点击时 APK 仍可能被替换或移除，最终响应由下载接口决定；页面
不捕获系统下载完成、暂停、失败或安装结果。

## 研究问题 6：服务端和统计是否需要调整

不需要服务端代码或新 API：

- metadata/download 两个 operation、错误格式、完整性校验、`no-store` 均保持。
- 正常主页 metadata 请求仍记录 `page_view`。
- 只有用户实际点击可用入口并请求 APK 时才产生 `download_request`。
- metadata 不可用时不会产生 APK 请求，这是新的前端门禁结果，不是统计故障。

需要更新 OpenAPI 中文说明和共享 UI 契约，移除“metadata 失败仍保持下载可达”和
“备用入口 fetch 下载中/失败态”的旧客户端约定。

## 最终决策摘要

| 决策点 | 采用 | 不采用 |
|--------|------|--------|
| 下载执行 | 浏览器原生链接 | fetch/Blob/object URL |
| 可用性 | metadata 单次三态门禁 | 静态 manifest 或失败后仍可点 |
| 进度 | 浏览器系统 UI | 页面内“99%”或伪进度 |
| 错误 | metadata 前置不可用 + 下载接口原生失败 | 页面读取 APK 后捕获响应 |
| 服务端 | 保持现状 | 新端点、代理下载、Range 本期改造 |
| 状态复用 | 两处共享 Provider/动作语义 | Hero 与中下部各自实现 |
