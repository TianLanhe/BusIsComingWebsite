# 功能规格：在线路线查询性能优化

**功能分支**：`codex/009-route-query-performance`

**创建日期**：2026-07-01

**状态**：Draft

**输入**：用户描述："按讨论优化后端在线路线查询性能：先实现 StopClient 1 天缓存，再实现 showstops2 stop map 1 天缓存，最后做 T/F/W 并发查询；保留现有地点和路线短缓存；暂不做 in-flight 去重。"

## 用户场景与测试（必填）

### 用户故事 1 - 复用稳定站名（优先级：P1）

网站访客在短时间内重复查询相近或相同路线时，路线卡应继续显示当前语言的准确上车站和下车站，并减少重复解析同一 stop id 带来的等待。

**优先级原因**：站名补齐会在路线卡展示中反复出现；先减少同一 stop id 的重复外部查询，可以降低上游依赖压力并改善重复查询体验。

**独立测试**：使用同一个已成功补齐站名的 stop id，在 1 天有效期内分别以繁体、简体、英文路线结果查询触发站名展示；确认当前语言站名一致可用，且重复查询不需要再次依赖同一 stop id 的外部站名响应。

**验收场景**：

1. **给定** 某个 stop id 已成功取得站名资料，**当** 1 天内再次需要展示同一 stop id 的当前语言站名，**则** 系统显示与首次成功结果一致的当前语言站名。
2. **给定** 某个 stop id 的站名资料取得失败或资料为空，**当** 用户再次查询包含该 stop id 的路线，**则** 系统不得复用失败结果，并仍按既有降级方式显示可用的站点名称。

---

### 用户故事 2 - 复用路线站点地图（优先级：P2）

网站访客看到多条路线卡或重复查询同一路线组合时，上车站、下车站和首程 ETA 所需的站点定位应复用已成功解析的路线站点地图，避免同一 P2P 路线资料在 1 天内反复重新解析。

**优先级原因**：路线卡站点预览和首程 ETA 都依赖同一类站点地图资料；缓存成功结果可以同时改善展示稳定性和后续 ETA token 的 stop id 补齐。

**独立测试**：使用同一组 P2P 路线资料和语言重复查询路线；确认 1 天内路线卡站点预览和 ETA stop id 解析结果一致，过期后会重新取得最新资料，失败结果不被缓存。

**验收场景**：

1. **给定** 某组 P2P 路线资料和语言已成功解析出非空站点地图，**当** 1 天内再次解析同一组资料，**则** 系统复用该站点地图并展示一致的上车站、下车站和 stop id。
2. **给定** 站点地图解析失败、返回空结果或外部服务不可用，**当** 用户再次查询同一路线组合，**则** 系统不得把失败状态作为 1 天缓存结果，并继续尝试按既有降级策略取得可用资料。

---

### 用户故事 3 - 并行搜索路线模式（优先级：P3）

网站访客发起在线路线查询时，系统应同时尝试既有的三种路线搜索模式，使基础路线摘要更快返回；同时结果内容、去重、排序和部分失败降级行为必须与现有体验保持一致。

**优先级原因**：三种路线搜索模式彼此没有用户可见的先后依赖；并行执行可以减少等待时间，但必须在缓存和稳定排序之后再做，以免放大上游请求或造成结果抖动。

**独立测试**：模拟三种搜索模式存在不同响应时间、部分失败和重复路线的情况；确认用户看到的路线摘要仍按既有规则去重和排序，且只要至少一种模式返回可用路线，查询就能成功。

**验收场景**：

1. **给定** 三种路线搜索模式都成功但响应时间不同，**当** 用户查询路线，**则** 系统返回合并后的路线摘要，等待时间接近最慢成功模式而不是三种模式耗时相加。
2. **给定** 其中一种或两种搜索模式失败，**当** 其他模式返回可解析路线，**则** 用户仍能看到可用路线结果，且失败模式不会清空成功结果。
3. **给定** 三种搜索模式都失败或都没有可解析路线，**当** 用户查询路线，**则** 系统返回既有的外部服务不可用降级状态。

---

### 边界情况

- 当缓存条目达到 1 天有效期后，系统必须重新取得站名或站点地图资料，避免长期展示过旧信息。
- 当同一 stop id 在不同语言下展示时，系统必须按当前语言选择站名；缓存不得导致简体、繁体或英文站名串用。
- 当站名资料缺少当前语言字段时，系统必须沿用既有语言回退规则，不得展示空白站名。
- 当站点地图或站名外部服务失败时，系统必须保留现有路线摘要降级行为，不得编造 stop id、站名或 ETA。
- 当三种路线搜索模式并行返回顺序不同，系统必须保持结果去重和排序稳定，不得因完成顺序导致同一输入出现随机排序。
- 当多个路线结果引用同一 P2P 路线资料或同一 stop id，系统可以在成功结果写入缓存后复用；本轮不要求合并同时进行中的重复请求。
- 当用户切换 `zh-Hant`、`zh-Hans`、`en` 后重新查询，动态地点和站名只展示当前语言一种，且不得出现跨语言缓存污染。
- 当用户期待完整出行路线规划、地铁或其他非香港巴士查询时，本功能不得扩大在线查询范围。
- 当服务端内部错误、panic 或并发任务异常发生时，系统必须恢复为受控错误或降级状态，并记录脱敏日志，避免服务整体崩溃。

## 需求（必填）

### 功能需求

- **FR-001**：系统必须为成功取得的站名资料提供 1 天有效复用能力，使同一 stop id 在有效期内可重复用于当前语言站名展示。
- **FR-002**：系统必须保证站名缓存不缓存失败、空结果或无法解析的资料。
- **FR-003**：系统必须保证站名展示按当前语言选择，并沿用既有语言字段回退规则；缓存不得导致跨语言串用。
- **FR-004**：系统必须为成功解析且非空的 P2P 站点地图提供 1 天有效复用能力，使同一 P2P 路线资料和语言在有效期内可重复用于路线卡站点预览和首程 ETA stop id 解析。
- **FR-005**：系统必须保证 P2P 站点地图缓存不缓存外部失败、空结果或无法解析的资料。
- **FR-006**：系统必须保留现有地点短缓存和路线短缓存，不因新增站点缓存而移除或改变其用户可见行为。
- **FR-007**：系统必须继续避免对实时 ETA 做长时间缓存；ETA 查询结果必须保持实时查询和既有 token 去重语义。
- **FR-008**：系统必须在路线查询时同时尝试既有三种路线搜索模式，并在合并结果时保持确定的去重和排序规则。
- **FR-009**：系统必须在部分路线搜索模式失败时保留成功模式的可解析路线结果；只有所有模式都失败或都没有可解析路线时，才返回路线查询不可用。
- **FR-010**：系统必须确保并行路线搜索不会把外部请求放大为无界并发；并发范围必须固定、可解释、可测试。
- **FR-011**：系统必须保证新增缓存和并行搜索不改变前端请求字段、响应字段、错误 envelope 或已有 OpenAPI 契约。
- **FR-012**：系统必须在日志或等价观测信息中保留缓存命中、外部查询降级和路线查询结果数量的定位能力，同时避免输出 token、完整外部 URL、第三方原始响应或 HTML。
- **FR-013**：系统必须为缓存过期、缓存命中、失败不缓存、语言隔离、部分模式失败和结果排序稳定性提供可重复验证。
- **FR-014**：系统不得新增用户定位、反向地理编码、路线详情页、非巴士查询或前端 UI 变化作为本功能范围的一部分。

### 关键实体（涉及数据时填写）

- **站名资料**：由 stop id 对应的多语言站名字段组成，用于路线卡上车站和下车站当前语言展示。
- **P2P 站点地图**：由 P2P 路线资料、语言和一组站点组成，用于定位上车站、下车站和首程 ETA 所需 stop id。
- **路线搜索模式结果**：单个路线搜索模式返回的路线候选集合，可能成功、失败或没有可解析路线。
- **路线查询结果**：面向前端的合并路线摘要，包含路线号链、站点摘要、价格、耗时、步行距离和可选 ETA token。
- **缓存条目**：稳定资料成功取得后的可复用记录，包含有效期、命中状态和用于隔离语言或资料来源的 key。

## 成功标准（必填）

### 可衡量结果

- **SC-001**：同一 stop id 在 1 天内重复用于路线结果站名展示时，第二次及后续展示能复用已成功取得的站名资料，且当前语言站名与首次成功结果一致。
- **SC-002**：同一 P2P 路线资料和语言在 1 天内重复用于路线卡站点预览或首程 ETA stop id 解析时，第二次及后续解析能复用已成功取得的站点地图，且上车站、下车站和 stop id 结果一致。
- **SC-003**：在代表性重复路线查询中，稳定站点资料相关外部请求数量相较当前实现至少减少 80%，同时用户看到的路线摘要字段不减少。
- **SC-004**：在三种路线搜索模式响应时间不同的代表性场景中，基础路线摘要等待时间相较串行模式至少降低 30%，且路线去重和排序结果保持稳定。
- **SC-005**：当任意一种或两种路线搜索模式失败时，只要至少一种模式返回可解析路线，用户仍能看到路线结果；当三种模式都不可用时，用户看到既有不可用降级状态。
- **SC-006**：缓存过期后，系统会重新取得站名或站点地图资料；失败、空结果和不可解析资料不会在 1 天内阻止后续重试。
- **SC-007**：本功能完成后，前端请求、响应结构、错误 envelope 和用户可见固定文案保持不变，现有在线查询页面无需修改即可继续工作。
- **SC-008**：后续维护者能从规格和文档中明确分辨哪些资料缓存 1 天、哪些资料保留短缓存、哪些实时资料不得长缓存。

## 假设

- 保留 backend 当前地点 5 分钟缓存和路线 1 分钟缓存，因为它们是网站公开试用接口的容量保护，不要求与 Android 主项目完全一致。
- 本轮只做成功结果 TTL 缓存，不实现 in-flight 去重；如果后续压测发现同时重复请求仍明显放大，再单独评估。
- 站名和 P2P 站点地图属于相对稳定资料，1 天有效期与 Android 主项目当前缓存策略一致。
- ETA 属于实时资料，本轮不新增长时间 ETA 缓存，只保留既有批量 token 去重和受控并发查询。
- 三种路线搜索模式是既有能力，本轮只优化执行编排，不改变路线搜索范围、路线字段含义或排序目标。
- 本功能不改变前端 UI、不新增用户可见文案、不新增 HTTP endpoint；OpenAPI 源文件应保持响应契约不漂移。
- 所有缓存仅作为服务进程内优化；服务重启后可以丢失，不要求跨实例共享。
