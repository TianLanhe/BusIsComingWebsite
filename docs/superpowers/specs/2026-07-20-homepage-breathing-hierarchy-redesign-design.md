# BusIsComing 首页呼吸感与强层级重设计

日期：2026-07-20

状态：设计已按用户反馈收敛，等待用户审阅本文档。

## 背景

当前首页已经具备现代、克制、清爽的基础视觉，但存在三个影响第一印象的问题：

1. 首屏信息过多，标题、说明、功能点、CTA、下载信息、信任信息和产品截图同时争夺注意力。
2. 背景基本静态，缺少用户要求的“随风轻轻飘动、波浪般呼吸”的感受。
3. 多个页面区块视觉权重接近，用户第一眼不够明确地知道先看哪里、下一步点哪里。

本设计采用用户选择的 B 方向：“聚焦式产品叙事”。它不是在现有页面上单纯增加动效，而是同步重排信息权重，让页面从第一屏开始形成清晰阅读顺序。

## 设计目标

- 首屏第一眼必须识别 BusIsComing 是香港巴士到站与路线查询 App。
- 页面整体保持克制、精简、简洁，不做夸张营销风格。
- 背景动效必须可感知，但不能抢走标题、CTA 和产品界面的视觉焦点。
- 页面向下滚动时不得出现底部深色潮汐层、固定波浪或干扰长页面阅读的装饰。
- 桌面端和手机端必须同等可用，主标题、下载入口、在线查询入口和语言切换在两端都清晰。
- 用户可见文案必须支持 `zh-Hant`、`zh-Hans` 和 `en`，并分别使用自然可信的产品表达。

## 方案决策

采用 B 方案：聚焦式产品叙事。

被确认的核心方向：

- Hero 只保留产品识别、核心标题、短说明、一个主 CTA、一个次 CTA 和真实产品界面信号。
- 原本并列的六个功能点压缩为三个证明点，降低首屏后的信息噪音。
- 在线路线查询成为第二视觉焦点，比普通功能卡更重要。
- 下载区作为页面末端的强转化区，但保持浅色收束，不使用深色底部波浪。
- FAQ、反馈和联系开发者保留为次要信息，视觉权重降到页面末端。

不采用的方向：

- 不采用底部深色潮汐动作，因为页面可持续向下滚动，深色底浪会制造错误的页面边界并干扰后续内容。
- 不采用紫色、蓝紫色或离散色块作为背景装饰，避免偏离品牌和用户已确认的海绿色方向。
- 不采用沉浸式滚动故事或滚动劫持，因为复杂动效会削弱克制感和可访问性。

## 信息架构

页面顺序调整为：

1. Header：品牌名、核心导航、语言切换。
2. Hero：产品识别、主标题、短说明、下载 CTA、试用查询 CTA、产品界面。
3. ProofStrip：三个证明点，分别对应查路线、看抵达、常用收藏。
4. OnlineQuery：在线查询区，作为第二主任务。
5. UseCases：两个轻量场景，解释通勤前查看常用站和临时出门搜索路线。
6. DownloadCTA：页面末端强下载区。
7. FAQ / Feedback / Contact / Footer：低视觉权重的支持信息。

桌面端可以使用宽屏节奏强化 Hero 与 OnlineQuery。移动端按相同顺序纵向排列，首屏需要露出下一段内容的一部分，避免像封闭海报。

## 视觉系统

色彩：

- 主色保留海绿和深青，服务香港巴士查询产品的清晰、可靠、轻量感。
- 背景只允许白、浅青、浅海绿、低饱和绿色过渡。
- 不使用紫色块、蓝紫渐变、强烈霓虹色或大面积深色底部装饰。

排版：

- Hero 标题使用最大字号，承担第一视觉焦点。
- Section 标题明显小于 Hero，避免每段都像首屏。
- Proof、FAQ、联系等辅助信息使用更低字号和更轻背景。
- 字体不得随 viewport 宽度线性缩放；使用断点、最大宽度和换行控制文本。

布局：

- 页面段落使用全宽区块或约束内容区，不把整个页面堆成漂浮卡片。
- 卡片只用于重复项、查询结果、场景说明等局部内容。
- 主要 CTA 不超过两个，避免首屏决策过载。

## 动效设计

Hero 背景使用“呼吸风带”：

- 由大面积模糊的水平浅色风带组成，颜色在海绿、浅青和白之间轻微漂移。
- 循环周期约 9 到 12 秒，实际可感知节奏控制在 5 到 8 秒内出现变化。
- 动效只改变位移、透明度和轻微纵向缩放，不做复杂路径和高频闪烁。
- 动效层位于 Hero 背景，不覆盖文字和 CTA，不进入后续主要内容区。

降级规则：

- `prefers-reduced-motion: reduce` 下关闭持续背景动画，保留静态浅色背景。
- 查询加载态不得使用强闪烁效果；可以使用低强度 skeleton 或静态占位。
- 页面滚动时不做滚动劫持、不做固定背景波浪、不做大面积视差。

## 组件边界

建议将前端拆为以下组件或等价边界：

- `Header`：品牌、导航、语言切换。导航保留功能、查询、下载三个主锚点，联系入口移到底部。
- `Hero`：主标题、短说明、主次 CTA、产品界面展示和背景呼吸层。
- `BreathingBackground`：只负责 Hero 背景动效，接受 reduced motion 状态，不承载业务内容。
- `ProofStrip`：三个简洁证明点，替代同权重的多功能卡片网格。
- `OnlineQuery`：现有路线查询体验的视觉重排，覆盖输入、加载、结果、空结果、错误和重试。
- `UseCaseSection`：两个场景说明，不新增产品能力，不暗示完整出行规划。
- `DownloadCTA`：下载 App、版本信息、Android 支持状态和必要下载说明。
- `SupportFooter`：FAQ、反馈、联系开发者、隐私和语言入口。

`OnlineQuery` 应继续消费既有前后端契约。除非后续实现计划另有明确批准，本设计不新增 HTTP API、不修改 OpenAPI schema、不改变后端查询范围。

## 数据与状态流

Hero、Proof、UseCases、Download 和 Footer 的文案应进入现有 i18n 内容系统或等价内容结构，覆盖 `zh-Hant`、`zh-Hans` 和 `en`。

OnlineQuery 状态流：

1. 默认状态：显示输入框、提示文案和必要示例，不展示虚假的实时数据。
2. 加载状态：保留用户输入，展示低强度加载占位。
3. 结果状态：展示路线号、方向、站点或摘要、到站时间或可用状态。
4. 空结果状态：提示找不到相关路线，建议检查路线号或改用站点搜索。
5. 错误状态：保留输入内容，说明暂时无法取得资料，并提供重试。

错误和降级不得编造实时到站结果。动态路线、站点和 ETA 事实必须来自现有查询服务或可追溯 fixture。

## 三语文案要求

默认语境以 `zh-Hant` 服务香港用户：

- `zh-Hant` 使用自然香港产品页面表达，例如“巴士幾時到，一眼就夠。”、“下載 Android App”、“試用路線查詢”。
- `zh-Hans` 使用自然简体中文，不只做繁简转换。
- `en` 使用克制的英语产品表达，例如 “Know when your bus arrives.”、“Download Android app”、“Try route search”。

所有按钮、查询状态、错误提示和 FAQ 条目必须在三语下验证不溢出、不遮挡、不改变主要布局。

## 响应式设计

桌面端：

- Hero 可以使用左侧文案、右侧产品界面信号的组合，但首屏整体仍应露出下一段证明点的一部分。
- OnlineQuery 使用说明和查询工具并列，让它成为第二视觉焦点。
- 下载区使用浅色强 CTA，不用深色底部压住页面。

移动端：

- Header 收敛为品牌、语言和菜单。
- Hero 纵向排列，优先显示标题、说明、下载 CTA，再显示产品界面。
- 次 CTA 可以位于主 CTA 下方或进入首屏下沿，但不得挤压标题可读性。
- OnlineQuery 必须完整可操作，输入、结果、空状态和错误状态不能依赖 hover。

## 可访问性与性能

- 所有 CTA、语言切换、查询输入和重试操作必须可键盘访问。
- 交互状态必须有可见 focus 样式。
- 动效不得导致文本对比度下降；背景层与前景文本之间需要稳定遮罩或足够透明度控制。
- `prefers-reduced-motion` 必须关闭持续背景动画。
- 背景动效应优先用 CSS transform 和 opacity 实现，避免高频 layout 或 paint。
- 不新增大型渲染库；不使用视频作为背景动效。

## 验证标准

实现完成后至少需要以下验证：

- 桌面 1440px 截图：首屏主标题和下载 CTA 是第一视觉焦点，下一屏内容有轻微露出。
- 手机 390px 截图：标题、下载 CTA、产品界面和下一段入口不重叠、不截断。
- 动效检查：背景可感知、有呼吸感，没有紫色块，没有底部深色波浪。
- Reduced motion 检查：关闭持续背景动画后页面仍完整可读。
- OnlineQuery 状态检查：默认、加载、结果、空结果、错误五类状态都可见且三语可容纳。
- i18n 检查：`zh-Hant`、`zh-Hans`、`en` 所有新增文案齐备，并在桌面和手机下无溢出。
- 契约检查：若仅做本设计范围内的前端呈现调整，OpenAPI 源契约不得漂移。
